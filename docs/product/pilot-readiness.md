# Pilot readiness: implemented product slice and remaining dependencies

This checklist separates code in the repository from controls that require a customer environment, independent assessment, or service operations. A successful compile does not mean the product is production-certified or that a customer's SSO works.

## Repository work completed in this slice

- Tenant admin APIs provision organizations from the verified issuer-to-tenant mapping and create venues, locations, events, and people. Requests cannot select an organization ID.
- Tenant administrators can inspect a paginated tenant-scoped audit feed from Setup for issue lifecycle, operational task, people provisioning, and event closeout changes. The feed exposes actor, action, resource reference, timestamp, and field names; it never returns before/after record payloads.
- Organization bootstrap and venue, location, and event creation are recorded in an append-only tenant-scoped setup audit table. The admin feed reports these resource changes without storing their record contents.
- `tenant:admin` gates tenant setup on the API. `operations:read` and `operations:write` gate event task access alongside signed venue/event/location scopes.
- Plan, Staffing, Service, and Stock task records have tenant/event/location consistency constraints, row-level security, and append-only audit events.
- Stock has a first-class venue catalog, event count workflow, and location transfer workflow: blind expected quantities during entry, independent scoped approval, stale-balance conflict detection, append-only count and transfer audit, dispatch-time source deduction, receipt-time destination credit, and reasoned short-receipt reconciliation. Transfers require a different scoped operator to confirm receipt. The Flutter Stock tab supports venue/location counts and transfer request, dispatch, receipt, cancellation, and tenant-admin catalog creation. Purchase orders, recipe depletion, and POS/inventory vendor synchronization remain gaps.
- Hospitality requests have an event-scoped API and Flutter queue with order line snapshots, location and service time, durable encrypted offline drafts, requester and kitchen capability boundaries, preparation and pickup transitions, reasoned rejection/cancellation, append-only audit, and durable assignment/status notifications. Kitchen staff can record cumulative per-line fulfillment batches and item substitutions; the database enforces requested-quantity ceilings, stores each batch in a tenant-scoped immutable table, requires reasons for substitutions and partial fulfillment, and keeps partially distributed orders open through event closeout. Menu/BEO linking, approval thresholds, kitchen batching, and delivery proof remain gaps.
- Event staffing now has first-class audited shifts with scoped assignment, draft/publish/cancel, worker acknowledgement or decline, self-claim for open published shifts, and server-timestamped check-in/check-out. Published schedule edits increment the shift revision and require a fresh worker response. Overlap checks block conflicting published assignments and serialize publish, claim, and schedule-update decisions per worker. Managers may publish explicit open slots; only an active, event-scoped worker can claim one. Scoped schedulers can review recorded unavailability for their assignable roster in a week-by-week calendar; private notes and out-of-scope people are never returned.
- Workers can record and remove their own unavailable time in Staffing. Entries are tenant-isolated, append-only audited (removal is a soft delete), and serialized with schedule changes. Assignment, publication, and self-claim are blocked when the shift overlaps recorded unavailable time.
- Tenant admins can grant or revoke roster qualifications with optional expiration dates. Shifts may require qualification codes; API checks active, unexpired records at assignment, publication, worker acknowledgement, open-shift claim, and check-in. Credential grants/revocations are included in the tenant audit feed. Admins can upload a private PDF or image, review a short-lived signed download, and verify or reject the evidence with a required rationale; evidence metadata and review outcome are tenant-scoped and audited. A pending or rejected evidence upload cannot satisfy a shift requirement; an explicit administrator attestation with no uploaded document remains eligible.
- Tenant admins must explicitly configure the minimum rest interval between shifts (0–1440 minutes) before assigning workers. Schedule writes enforce the configured interval transactionally, and increasing the policy is rejected if it conflicts with already published future shifts. The default is unconfigured because the venue's labor agreement and jurisdiction define the appropriate value.
- Shift publication, material schedule edits, and cancellation create durable recipient-scoped inbox notices in the same transaction; configured device push uses generic text, and opening the notice navigates to the affected event schedule.
- Venue, location, event, person, and operational-task writes use tenant-scoped idempotency receipts; the Flutter client retains pending keys securely across transport failures and rejects key reuse with a changed command.
- The signed-in Flutter experience now loads its organization and event data from `/api/v1/me`, uses the real issue list and task endpoints, replaces the client-side role picker with IdP capabilities, and exposes the admin setup flow.
- Signed-in navigation adapts to the workspace width: phones use a capability-prioritized bottom bar with overflow for the remaining authorized workflows, tablets use a compact destination rail, and desktop uses a persistent labeled sidebar. Widget tests cover phone overflow selection, tablet navigation, and desktop navigation. The feature pages are not yet full desktop planning workspaces with split details, data grids, saved views, and bulk actions; those remain design and implementation work.
- Today now aggregates live event data into a role-scoped attention list: critical/high issues, blocked operations tasks, overdue work, submitted stock counts, active hospitality orders, vendor staffing requests, and manager-visible coverage gaps are prioritized and link directly to their workflow. It also shows live metrics for issues, tasks, shifts, stock approvals, hospitality, vendor requests, and unfilled positions when the signed capabilities permit. A recent-update list surfaces the latest active issue/task changes; unavailable endpoints retain explicit error and refresh guidance, and refresh reloads all displayed feeds.
- The Issues view subscribes to the scoped replayable SSE stream, refreshes the issue list when a server event arrives, resumes from its last event ID after reconnect, and shows connection state.
- Issue triage, assignment, escalation, resolution, verification, and closure invoke the existing audited, idempotent API transitions. Pending or failed offline issue reports are visible in a per-event queue and can be retried.
- Issue assignment and resolution create durable in-app notifications in the same transaction as the issue transition. Notification reads are restricted to the verified recipient subject by PostgreSQL RLS; users can mark their own notifications read in the app.
- Opt-in FCM/APNs device alerts now register, rotate, and revoke per-user device tokens under tenant RLS. Alerts are generic and non-sensitive; durable inbox rows remain the source of truth if push delivery fails.
- SCIM 2.0 exposes tenant-scoped user list/create/read/replace/patch/deactivate endpoints. It provisions the roster only; capability and venue/event scope remain controlled by signed identity-provider claims. SCIM `externalId` must match the API's canonical `issuer|sub` subject so deactivation is checked on every authenticated API request. Tenant bearer tokens are compared by digest and belong in pinned Secret Manager versions.
- A signed integration ingestion endpoint stores idempotent, tenant-scoped normalized external events and exposes them to authorized event operators. `operations.task.upserted` events create or refresh API-backed Plan, Staffing, Service, or Stock tasks with source ownership, venue checks, and audit history. The envelope, HMAC contract, replay rules, and data-minimization requirements are documented in `docs/integrations/signed-event-ingestion.md`; vendor-specific connectors and field mappings are still required.
- Issue reports support up to five encrypted-at-rest local photo attachments. The API creates private Cloud Storage uploads with short-lived signed URLs, verifies content type, byte count, and SHA-256 before marking an attachment ready, and returns short-lived signed download links to authorized issue readers.
- Issue reporters may explicitly attach foreground device-location evidence. The app requests permission only after the reporter taps the location action, stores the coordinates, reported accuracy, and capture time in the encrypted offline outbox, and submits them with the report. API validation requires a complete coordinate/accuracy/time tuple, valid ranges, and a non-future capture time. Coordinates are returned only with tenant/event/location-scoped issue records. This is user-reported device data and does not prove physical presence; customers must set retention and privacy policy before enabling it operationally.
- Offline issue reporting uses the encrypted secure-storage outbox and retries when connectivity returns. Previously loaded organization/event bootstrap, issue, and task lists are cached in secure storage per signed-in identity and capability scope for up to 12 hours; cache reads are used only for transport failures, not authorization/server responses. Pending reports are bound to their originating session scope and cannot be replayed under a different login.
- iOS release workflow requires the repository variable `VENUE_API_BASE_URL`, rejects a non-HTTPS value, and passes the selected URL as a Dart define. It fails closed when the value is missing.
- GitHub CI now provisions separate non-superuser migrator/runtime roles in PostgreSQL 17, applies the complete migration chain as `venue_migrator`, seeds two isolated tenants, runs the RLS integration suite as `venue_app`, and runs Prisma validation, client generation, API build/tests, high-severity npm audit, and Flutter analysis/tests. Dependabot checks npm, Flutter pub, and GitHub Actions dependencies weekly. Production dependency overrides are pinned to patched `deepmerge-ts` and `uuid` lines and verified by the API build/test suite.
- The manual Cloud Run deployment workflow uses GitHub OIDC/Workload Identity Federation, pinned Secret Manager version variables, a no-traffic tagged candidate, and the API RLS health gate before promoting traffic. It does not run database migrations.
- Event closeout collects unresolved issues, tasks, attendance claims, hospitality orders, stock counts, and transfers into a scoped, audited review. Each exception must be resolved, explicitly accepted with a reason, or assigned to an in-scope owner with a due date. Finalization rechecks live state; database triggers block ordinary mutations after closure. Outcome summaries can be saved to an encrypted, identity-and-capability-scoped offline outbox and sync only while closeout remains open; conflicts remain on-device for review. Managers can add reasoned, tenant-scoped, immutable post-close correction addenda linked to an event source record without unlocking or rewriting the original record.
- The API health gate includes RLS and FORCE RLS for all 44 protected application data tables. CI tenant isolation checks cover setup, people, tasks, shifts, availability, qualifications, breaks, coverage demand, pending attendance claims, stock count and transfer workflows, hospitality orders and fulfillment, event closeout, vendor staffing requests/audit, and append-only post-close correction records. Offline attendance timestamps remain unverified until a scoped supervisor accepts or rejects them with a reason. Operational tasks, notifications, issue evidence, signed integration events, and owner-scoped push devices are checked alongside issue records. Re-run those checks against approved staging before a customer rollout. Person mutations create append-only, tenant-scoped audit entries without duplicating personal field values.
- Staffing now checks recorded unavailability, schedule overlaps, configured minimum rest intervals, and admin-attested or reviewed qualification validity. Managers can request scoped eligible-worker recommendations for a draft shift. The API filters against assignable roster scope, recorded unavailable intervals, published shifts/rest windows, current required qualifications, and configured tenant rest policy, then ranks eligible candidates by scheduled event minutes; the manager confirms the assignment and the write path rechecks every rule. “No recorded conflict” is not a confirmed availability signal, and the system does not automatically assign or publish shifts. Schedulers can review roster unavailability in a week-by-week calendar, but the product does not distinguish “no block recorded” from confirmed availability. Managers can record role-, area-, and time-specific staffing demand; coverage reports count existing draft and published shifts that cover the complete demand window, and one action generates only the remaining deficit as auditable draft open shifts. Assigned workers can record server-timestamped meal/rest break start and end while checked in; tenant-scoped RLS, a one-active-break constraint, checkout guard, and append-only shift audit protect the workflow. Offline attendance uses the encrypted device outbox and remains explicitly pending until supervisor review with a reason. Scoped supervisors can correct recorded check-in/check-out times with a required reason; each correction preserves before/after values in the append-only audit history and is blocked while offline claims await review. Remaining gaps include full automatic assignment/optimization and vendor commitments.
- Managers can request a historical coverage baseline for a future event. The API compares manager-entered demand windows from up to 20 earlier events at the same tenant venue, groups matching role/area/time windows, and estimates headcount with a median; common qualification requirements are retained. The response identifies its source and sample count, flags fewer than three matching events as limited history, and never writes demand or creates shifts. The app lets the manager review and edit a suggestion before saving. This is a baseline from prior staffing plans, not a forecast trained on attendance, ticket sales, or live operational data; full automatic assignment/optimization remains a gap. Vendor requests now have a tenant-scoped workflow; vendor-specific labor/POS/ticketing adapters still need customer APIs and mapping requirements.
- Vendor staffing now has a manual, API-backed event workflow: managers can send an idempotent request against a recorded uncovered demand gap to an in-scope active user, with a response deadline and event instructions; that recipient alone can acknowledge, partially commit, commit, or decline. Managers can cancel requests or record fulfillment after a commitment. Tenant-scoped RLS and immutable audit protect request history, durable in-app notifications and opt-in generic push announce transitions, and open vendor requests appear in event closeout. A commitment is not a named roster assignment or verified attendance, and there is no vendor connector/dispatch integration or automated deadline escalation yet.
- Added a private vulnerability-reporting policy, an event-day incident/release runbook, a pilot security evidence register, and a support agreement worksheet. These templates make implementation evidence and unresolved decisions visible; they do not constitute an audit attestation, legal agreement, staffed support service, or SLA.

## Required before a customer pilot

1. **Choose and deploy the API.** Set GitHub Actions variable `VENUE_API_BASE_URL` to the actual HTTPS API origin after deploying the API. The repository does not contain a verified current API URL; do not use a guessed `run.app` name.
2. **Apply the database migrations through the approved migrator process.** CI replays the complete chain against a fresh PostgreSQL 17 database with separate non-superuser migrator/runtime roles. The chain includes `20260923000000_issue_vertical_slice`, `20260924000000_issue_locations`, `20260925000000_durable_issue_events`, `20260926000000_operations_admin`, `20260927000000_notifications`, `20260928000000_issue_evidence`, `20260929000000_scim_user_lifecycle`, `20260930000000_signed_integration_events`, `20261001000000_push_devices`, `20261002000000_external_task_mappings`, `20261003000000_tenant_setup_audit`, `20261004000000_staff_shift_workflow`, `20261005000000_staff_availability`, `20261006000000_person_qualifications`, `20261007000000_staff_rest_policy`, `20261008000000_staff_breaks`, `20261009000000_offline_attendance_claims`, `20261010000000_staffing_coverage`, `20261011000000_qualification_evidence_review`, `20261012000000_issue_location_evidence`, `20261013000000_inventory_count_workflow`, `20261014000000_hospitality_order_fulfillment`, `20261015000000_stock_transfers`, `20261016000000_event_closeout`, `20261017000000_vendor_staffing_requests`, `20261018000000_post_close_corrections`, and `20261019000000_hospitality_partial_fulfillment`; they have not been applied to the customer database. Confirm the target project and migration identity before rollout.
3. **Configure the tenant labor rule.** A tenant administrator must set the contracted minimum rest interval before assigning workers. Confirm the value against the venue's labor agreements and applicable local rules; the system does not determine the legal value.
4. **Configure customer Okta/Entra apps and claims.** Provision `SSO_PROVIDERS_JSON`; map least-privilege IdP roles to `issue:*`, `operations:*`, and narrowly assigned `tenant:admin`, plus current UUID scopes and assignable user subjects. Test token audience, client, issuer, group mapping, revocation, and successful API acceptance in each customer tenant.
5. **Onboard and scope the tenant.** An authorized administrator can create venue structure. An identity administrator still needs to assign the corresponding venue/event/location IDs and capabilities to user tokens.
6. **Configure evidence storage, provisioning, and mobile push.** Set production `EVIDENCE_BUCKET` to a private Cloud Storage bucket. Enable uniform bucket-level access and public access prevention; use a dedicated Cloud Run service identity with object create/read permissions and IAM signing permission for V4 upload policies, with no service-account key file. Configure `SCIM_PROVIDERS_JSON` with a different high-entropy bearer token for each tenant and `INTEGRATION_PROVIDERS_JSON` with HMAC secrets for approved sources, stored in Secret Manager. Follow `docs/release/push-notifications.md` to register Firebase apps, enable Apple Push Notifications, upload the APNs authentication key to Firebase, set GitHub Firebase variables, and grant `cloudmessaging.messages.create` to the API runtime identity. Apply migrations, then verify upload/download, SCIM lifecycle, signed event retries, and push on physical devices in staging. Vendor-specific labor/POS/ticketing adapters and MDM/Intune distribution remain unimplemented.
7. **Configure and exercise the deployment path.** Establish GitHub-to-GCP Workload Identity Federation, create least-privilege deployer/runtime identities, provision pinned Secret Manager versions, Artifact Registry, Cloud Run and the private bucket, then run the tagged-candidate health gate. Follow `docs/release/cloud-run-api.md`; no GCP resources or API deploy were created in this repository change.
8. **Agree integrations and distribution.** Map the vendor-specific labor/POS/ticketing APIs, field ownership, event mapping, retry behavior, and support contacts. Configure Apple Business Manager/Intune or the customer’s chosen MDM to distribute and update the signed iOS app; TestFlight alone is not managed-device deployment.
9. **Complete customer security and operations review.** Work through `docs/security/pilot-security-evidence-register.md` and complete `docs/operations/pilot-support-agreement-template.md` with the customer. SOC 2 evidence, independent penetration testing, DPA, insurance, agreed SLA, staffed incident response, monitoring, backups/restore evidence, and event-day support commitments must be supplied and approved; repository templates and gates do not create those attestations or commitments.

## Release verification still required

- No migration, deployment, authenticated customer IdP login, Cloud Storage validation, App Store Connect upload, or device validation was performed as part of this change.
- CI verifies the migration replay and runtime-role isolation on a clean PostgreSQL 17 database. Also run the suite against the approved disposable staging database and verify the `tenant:admin` and task authorization matrix before exposing these endpoints to a customer.
