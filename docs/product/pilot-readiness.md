# Pilot readiness: implemented product slice and remaining dependencies

This checklist separates code in the repository from controls that require a customer environment, independent assessment, or service operations. A successful compile does not mean the product is production-certified or that a customer's SSO works.

## Repository work completed in this slice

- Tenant admin APIs provision organizations from the verified issuer-to-tenant mapping and create venues, locations, events, and people. Requests cannot select an organization ID.
- Tenant admins can correct the organization's display name through a tenant-scoped idempotent endpoint without changing its verified tenant ID or identity-provider slug. Staff identity remains owned by Okta, Microsoft Entra ID, or SCIM; the first successful SSO bootstrap creates the profile, while manual roster creation requires the exact verified issuer/subject. This is not an invitation or IdP provisioning workflow.
- Venue setup records an IANA time zone and starts new venues in `DRAFT`. A tenant-admin readiness endpoint checks the time zone and presence of at least one location; activation and suspension are tenant-scoped, idempotent, and audited. Draft venues allow location setup, while event creation is rejected unless the venue is active, has a valid time zone, and has a location. The migration preserves existing venues as active, but legacy venues without a configured time zone must be corrected before new events can be created. Venue-admin delegation, templates, service-area/departments setup, customer acceptance, and event time display in the venue time zone remain open.
- Tenant administrators can inspect a paginated tenant-scoped audit feed from Setup for issue lifecycle, operational task, people provisioning, and event closeout changes. The feed exposes actor, action, resource reference, timestamp, and field names; it never returns before/after record payloads.
- Tenant administrators can activate or deactivate SSO/admin-managed roster records in Setup; self-deactivation is blocked. SCIM-managed users are visibly identified and their active state can only be changed through the identity provider/SCIM channel. Pre-existing records whose source cannot be inferred are marked `unknown` and require provenance reconciliation before local status changes. The API checks account status on every authenticated request and audits only changed field names.
- Organization bootstrap and venue, location, and event creation are recorded in an append-only tenant-scoped setup audit table. The admin feed reports these resource changes without storing their record contents.
- Tenant administrators can correct venue and location names, and event names or start times, through tenant-scoped idempotent update APIs and the Setup screen. Audits record changed field names only; finalized events are locked against metadata edits and require a post-close correction addendum instead.
- `tenant:admin` gates tenant setup on the API. `operations:read` and `operations:write` gate event task access alongside signed venue/event/location scopes.
- Plan, Staffing, Service, and Stock task records have tenant/event/location consistency constraints, row-level security, and append-only audit events.
- Stock has a first-class venue catalog, event count workflow, and location transfer workflow: blind expected quantities during entry, independent scoped approval, stale-balance conflict detection, append-only count and transfer audit, dispatch-time source deduction, receipt-time destination credit, and reasoned short-receipt reconciliation. Transfers require a different scoped operator to confirm receipt. Purchase requests now support venue/location catalog lines, independent manager approval, incremental physical receiving, inventory movement and on-hand updates, reasoned short closure, idempotency, event closeout, and tenant audit/RLS. The Flutter Stock tab supports venue/location purchasing alongside counts and transfer request, dispatch, receipt, cancellation, and tenant-admin catalog creation. Tenant administrators and operations managers can configure menu recipes using same-venue stock items. Non-substituted fulfillment decrements stock inside the hospitality transaction and appends an immutable stock movement; insufficient or inactive ingredients block the batch. Substitutions skip the original recipe. POS/inventory vendor synchronization remains a customer-specific gap.
- Hospitality requests have an event-scoped API and Flutter queue with order line snapshots, location and service time, durable encrypted offline drafts, requester and kitchen capability boundaries, preparation and pickup transitions, reasoned rejection/cancellation, append-only audit, and durable assignment/status notifications. Kitchen staff can record cumulative per-line fulfillment batches and item substitutions; the database enforces requested-quantity ceilings, stores each batch in a tenant-scoped immutable table, requires reasons for substitutions and partial fulfillment, and keeps partially distributed orders open through event closeout. Pickup requires a scoped in-person acknowledgement, receiver name, optional note, and a receiver signature captured in the app and stored in the immutable, tenant-scoped handoff receipt; pickup is blocked until every line is fulfilled. The optional receiver photo uses an encrypted local temporary file, a tenant- and order-scoped upload record, private Cloud Storage, server-side type/size/hash verification, and a short-lived scoped download link. Before the pickup dialog closes, the receiver name, note, acknowledgement, signature, optional photo metadata, and stable idempotency key are saved in the signed-in user's encrypted local queue. If offline or a request fails, the receipt remains visibly pending, the server order stays unchanged, and the encrypted photo remains available; the queue retries when connectivity returns and offers a manual retry. Only a successful server response removes the queued receipt and local photo. This is local-device recovery, not multi-device synchronization or proof of customer-device acceptance. The signature and photo are operational evidence, not a certified electronic signature. Orders can record and display an optional venue-provided BEO reference, including in encrypted offline drafts; this is a traceability field, not a menu import or synchronization. Tenant admins can configure an optional hospitality order approval threshold; orders exceeding the threshold enter an auditable `AWAITING_APPROVAL` state before submission to the kitchen, and scoped managers can approve or reject them. Venues have a tenant-scoped menu catalog with per-item pricing, default units, and active state; order lines can reference catalog items while retaining snapshot pricing. A threshold the tenant sets is not a legal rule. Vendor POS/inventory synchronization remains a customer-specific gap.
- Event staffing now has first-class audited shifts with scoped assignment, draft/publish/cancel, worker acknowledgement or decline, self-claim for open published shifts, and server-timestamped check-in/check-out. Published schedule edits increment the shift revision and require a fresh worker response. Overlap checks block conflicting published assignments and serialize publish, claim, and schedule-update decisions per worker. Managers may publish explicit open slots; only an active, event-scoped worker can claim one. Scoped schedulers can review recorded unavailability for their assignable roster in a week-by-week calendar; private notes and out-of-scope people are never returned.
- Workers can record and remove their own unavailable time in Staffing. Entries are tenant-isolated, append-only audited (removal is a soft delete), and serialized with schedule changes. Assignment, publication, and self-claim are blocked when the shift overlaps recorded unavailable time.
- Tenant admins can grant or revoke roster qualifications with optional expiration dates. Shifts may require qualification codes; API checks active, unexpired records at assignment, publication, worker acknowledgement, open-shift claim, and check-in. Credential grants/revocations are included in the tenant audit feed. Admins can upload a private PDF or image, review a short-lived signed download, and verify or reject the evidence with a required rationale; evidence metadata and review outcome are tenant-scoped and audited. A pending or rejected evidence upload cannot satisfy a shift requirement; an explicit administrator attestation with no uploaded document remains eligible.
- Tenant admins must explicitly configure the minimum rest interval between shifts (0–1440 minutes) before assigning workers. Schedule writes enforce the configured interval transactionally, and increasing the policy is rejected if it conflicts with already published future shifts. The default is unconfigured because the venue's labor agreement and jurisdiction define the appropriate value.
- Shift publication, material schedule edits, and cancellation create durable recipient-scoped inbox notices in the same transaction; configured device push uses generic text, and opening the notice navigates to the affected event schedule.
- Venue, location, event, person, and operational-task writes use tenant-scoped idempotency receipts; the Flutter client retains pending keys securely across transport failures and rejects key reuse with a changed command.
- The signed-in Flutter experience now loads its organization and event data from `/api/v1/me`, uses the real issue list and task endpoints, replaces the client-side role picker with IdP capabilities, and exposes the admin setup flow.
- Signed-in navigation adapts to the workspace width: phones use a capability-prioritized bottom bar with overflow for the remaining authorized workflows, tablets use a compact destination rail, and desktop uses a persistent labeled sidebar. Widget tests cover phone overflow selection, tablet navigation, and desktop navigation. The Issues workspace now adds desktop search/state filters and a selectable split list/detail view while retaining one-column issue cards on phones. Staffing adds event-scoped All, Needs action, Open shifts, and My shifts quick views with counts; these are transient client filters over authorized API data, not persisted saved views. A desktop schedule grid, saved views, and bulk actions remain open product work.
- Desktop users can press Ctrl+K (or Command+K) or select Search workflows to open a capability-filtered command palette. Event task creation offers Plan, Staffing, Service, and Stock categories; all four use the audited event-task API.
- Today now aggregates live event data into a role-scoped attention list: critical/high issues, blocked operations tasks, overdue work, submitted stock counts, active hospitality orders, vendor staffing requests, and manager-visible coverage gaps are prioritized and link directly to their workflow. It also shows live metrics for issues, tasks, shifts, stock approvals, hospitality, vendor requests, and unfilled positions when the signed capabilities permit. A recent-update list surfaces the latest active issue/task changes; unavailable endpoints retain explicit error and refresh guidance, and refresh reloads all displayed feeds.
- The Issues view subscribes to the scoped replayable SSE stream, refreshes the issue list when a server event arrives, resumes from its last event ID after reconnect, and shows connection state.
- Issue triage, assignment, escalation, resolution, verification, and closure invoke the existing audited, idempotent API transitions. Pending or failed offline issue reports are visible in a per-event queue and can be retried.
- On a shared device, issue and attendance queue controllers reset when the signed-in token changes. The issue queue restores only reports matching the current identity scope, preserves other users' encrypted pending reports without displaying or replaying them, and rechecks that scope before sending issue or photo requests. A failed secure save reports an error and cleans up its temporary photo files.
- Issue list snapshots are stored in encrypted platform secure storage under a key scoped to the signed-in organization, issuer, subject, capabilities, and assigned venue/event/location claims. Only connection failures and network timeouts may use an unexpired snapshot within the managed offline-cache limit; authorization responses, certificate failures, and canceled requests do not fall back to stale data. The client discards an in-flight response or cache fallback if the signed-in scope changes during the request. The Issues view labels cached data with its last successful refresh time, and explicit sign-out clears these snapshots.
- Issue assignment and resolution create durable in-app notifications in the same transaction as the issue transition. Notification reads are restricted to the verified recipient subject by PostgreSQL RLS; users can mark their own notifications read in the app.
- Opt-in FCM/APNs device alerts register, rotate, and revoke per-user device tokens under tenant RLS. Alerts are generic and carry only a notification ID and type; opening one resolves the recipient's durable inbox record, verifies the event remains assigned and the target workflow is capability-enabled, then routes to the issue, shift, hospitality order, closeout, or vendor workflow. Issue alerts select the referenced issue. Already-read inbox items remain navigable. Durable inbox rows remain the source of truth if push delivery fails.
- SCIM 2.0 exposes tenant-scoped user list/create/read/replace/patch/deactivate endpoints. It provisions the roster only; capability and venue/event scope remain controlled by signed identity-provider claims. SCIM `externalId` must match the API's canonical `issuer|sub` subject so deactivation is checked on every authenticated API request. Tenant bearer tokens are compared by digest and belong in pinned Secret Manager versions.
- A signed integration ingestion endpoint stores idempotent, tenant-scoped normalized external events and exposes them to authorized event operators. `operations.task.upserted` events create or refresh API-backed Plan, Staffing, Service, or Stock tasks with source ownership, venue checks, and audit history. The Operations view now lists accepted connector events by source, type, reference, and timestamp without returning imported payloads. The envelope, HMAC contract, replay rules, and data-minimization requirements are documented in `docs/integrations/signed-event-ingestion.md`; vendor-specific connectors and field mappings are still required.
- Issue reports support up to five encrypted-at-rest local photo attachments. The app removes the camera plugin's temporary source after reading it and accepts decrypt/delete paths only when they match a UUID-named file in the app's managed evidence directory. The API creates private Cloud Storage uploads with short-lived signed URLs, verifies content type, byte count, and SHA-256 before marking an attachment ready, and returns short-lived signed download links to authorized issue readers.
- Issue reporters may explicitly attach foreground device-location evidence. The app requests permission only after the reporter taps the location action, stores the coordinates, reported accuracy, and capture time in the encrypted offline outbox, and submits them with the report. API validation requires a complete coordinate/accuracy/time tuple, valid ranges, and a non-future capture time. Coordinates are returned only with tenant/event/location-scoped issue records. This is user-reported device data and does not prove physical presence; customers must set retention and privacy policy before enabling it operationally.
- Offline issue reporting uses the encrypted secure-storage outbox and retries when connectivity returns. Previously loaded organization/event bootstrap, issue, and task lists are cached in secure storage per signed-in identity and capability scope for up to 12 hours; cache reads are used only for transport failures, not authorization/server responses. If provider discovery or native token refresh has a recognized network failure after the access token expires, the app retains the encrypted session long enough to show permitted cached views with an offline banner and Retry action; it never sends the expired token to the API. A provider rejection still clears the session and cached views. Sign-out discards late refresh results and waits only for a credential write already underway before clearing local credentials. Pending reports are bound to their originating session scope and cannot be replayed under a different login.
- iOS release workflow requires the repository variable `VENUE_API_BASE_URL`, rejects a non-HTTPS value, and passes the selected URL as a Dart define. It fails closed when the value is missing.
- GitHub CI now provisions separate non-superuser migrator/runtime roles in PostgreSQL 17, applies the complete migration chain as `venue_migrator`, seeds two isolated tenants, runs the RLS integration suite as `venue_app`, and runs Prisma validation, client generation, API build/tests, high-severity npm audit, and Flutter analysis/tests. Dependabot checks npm, Flutter pub, and GitHub Actions dependencies weekly. Production dependency overrides are pinned to patched `deepmerge-ts` and `uuid` lines and verified by the API build/test suite.
- The manual Cloud Run deployment workflow uses GitHub OIDC/Workload Identity Federation, pinned Secret Manager version variables, a no-traffic tagged candidate, and the API RLS health gate before promoting traffic. It does not run database migrations.
- Event closeout collects unresolved issues, tasks, attendance claims, hospitality orders, stock counts, transfers, and purchase orders into a scoped, audited review. Each exception must be resolved, explicitly accepted with a reason, or assigned to an in-scope owner with a due date. Finalization rechecks live state; database triggers block ordinary mutations after closure. Outcome summaries can be saved to an encrypted, identity-and-capability-scoped offline outbox and sync only while closeout remains open; conflicts remain on-device for review. Managers can add reasoned, tenant-scoped, immutable post-close correction addenda linked to an event source record without unlocking or rewriting the original record.
- Latest verified CI, [run 36172087506](https://github.com/lwhobley/venuewranglerenterprise/actions/runs/36172087506) on commit `b2f30e6`, passed on 2026-09-25. It dynamically checked RLS coverage and runtime-role tenant isolation, replayed the committed migration chain through stock purchase orders, built and tested the API, audited API dependencies, and analyzed/tested Flutter. Offline attendance timestamps remain unverified until a scoped supervisor accepts or rejects them with a reason. Re-run the checks against approved staging before a customer rollout. Person mutations create append-only, tenant-scoped audit entries without duplicating personal field values.
- Staffing checks recorded unavailability, schedule overlaps, configured minimum rest intervals, and admin-attested or reviewed qualification validity. Managers can request scoped eligible-worker recommendations for a draft shift. The API filters against assignable roster scope, recorded unavailable intervals, published shifts/rest windows, current required qualifications, and configured tenant rest policy, then ranks eligible candidates by scheduled event minutes; the manager confirms the assignment and the write path rechecks every rule. For unassigned draft shifts, managers can also request explicit available/unavailable responses from eligible workers. Suggestions label confirmed availability separately from “no recorded conflict”; neither signal assigns a worker or acknowledges a published shift. The system does not automatically assign or publish shifts. Schedulers can review roster unavailability in a week-by-week calendar. Managers can record role-, area-, and time-specific staffing demand; coverage reports count existing draft and published shifts that cover the complete demand window, and one action generates only the remaining deficit as auditable draft open shifts. Assigned workers can record server-timestamped meal/rest break start and end while checked in; tenant-scoped RLS, a one-active-break constraint, checkout guard, and append-only shift audit protect the workflow. Offline attendance uses the encrypted device outbox and remains explicitly pending until supervisor review with a reason. Scoped supervisors can correct recorded check-in/check-out times with a required reason; each correction preserves before/after values in the append-only audit history and is blocked while offline claims await review. Remaining gaps include full automatic assignment/optimization and vendor commitments.
- For an unassigned draft shift, schedulers can now ask eligible, in-scope workers to explicitly report available or unavailable. Requests are scoped to the current shift revision, durable, tenant-isolated, audited, and announced through the durable inbox and optional generic push. Workers see that a response does not assign them. Managers can review responses; stale requests are rejected after the shift changes, assignment suggestions exclude workers who reported unavailable, and an explicit available response is identified separately from a schedule with no recorded conflict. This is a planning signal, not an assignment or published-shift acknowledgement. CI and the approved staging database must verify the new migration and RLS behavior before pilot use.
- Managers can request a historical coverage baseline for a future event. The API compares manager-entered demand windows from up to 20 earlier events at the same tenant venue, groups matching role/area/time windows, and estimates headcount with a median; common qualification requirements are retained. The response identifies its source and sample count, flags fewer than three matching events as limited history, and never writes demand or creates shifts. The app lets the manager review and edit a suggestion before saving. This is a baseline from prior staffing plans, not a forecast trained on attendance, ticket sales, or live operational data; full automatic assignment/optimization remains a gap. Vendor requests now have a tenant-scoped workflow; vendor-specific labor/POS/ticketing adapters still need customer APIs and mapping requirements.
- Vendor staffing now has a manual, API-backed event workflow: managers can send an idempotent request against a recorded uncovered demand gap to an in-scope active user, with a response deadline and event instructions; that recipient alone can acknowledge, partially commit, commit, or decline. Managers can cancel requests or record fulfillment after a commitment. Tenant-scoped RLS and immutable audit protect request history, durable in-app notifications and opt-in generic push announce transitions, and open vendor requests appear in event closeout. A commitment is not a named roster assignment or verified attendance, and there is no vendor connector/dispatch integration or automated deadline escalation yet.

## Required before a customer pilot

1. **Choose and deploy the API.** Set GitHub Actions variable `VENUE_API_BASE_URL` to the actual HTTPS API origin after deploying the API. The repository does not contain a verified current API URL; do not use a guessed `run.app` name.
2. **Apply the database migrations through the approved migrator process.** CI run `36172087506` on commit `b2f30e6` replayed the committed chain through `20261026000000_stock_purchase_orders` against fresh PostgreSQL 17 with separate non-superuser migrator/runtime roles. The current worktree adds migrations `20261027000000_hospitality_receipt_photo_evidence`, `20261028000000_hospitality_recipe_stock_depletion`, and `20261029000000_venue_activation_lifecycle`; all 37 migrations have now replayed locally on a disposable PostgreSQL 18 cluster using the repository's role/schema bootstrap, and the RLS integration suite passed as `venue_app`. This is local evidence only; CI verification after commit and approved customer/staging migration are still required. Confirm the target project and migration identity before rollout.
3. **Configure the tenant labor rule and hospitality approval threshold.** A tenant administrator must set the contracted minimum rest interval before assigning workers. Confirm the value against the venue's labor agreements and applicable local rules; the system does not determine the legal value. A tenant administrator may also configure an optional hospitality order approval threshold; a threshold the tenant sets is an operational control, not a legal rule.
4. **Configure customer Okta/Entra apps and claims.** Provision `SSO_PROVIDERS_JSON`; map least-privilege IdP roles to `issue:*`, `operations:*`, and narrowly assigned `tenant:admin`, plus current UUID scopes and assignable user subjects. Test token audience, client, issuer, group mapping, revocation, and successful API acceptance in each customer tenant.
5. **Onboard and scope the tenant.** An authorized administrator can create venue structure. An identity administrator still needs to assign the corresponding venue/event/location IDs and capabilities to user tokens. Before enabling local roster status changes for records carried forward from before provenance tracking, reconcile each `unknown` provisioning source against authoritative IdP/SCIM records.
6. **Configure evidence storage, provisioning, and mobile push.** Set production `EVIDENCE_BUCKET` to a private Cloud Storage bucket. Enable uniform bucket-level access and public access prevention; use a dedicated Cloud Run service identity with object create/read permissions and IAM signing permission for V4 upload policies, with no service-account key file. Configure `SCIM_PROVIDERS_JSON` with a different high-entropy bearer token for each tenant and `INTEGRATION_PROVIDERS_JSON` with HMAC secrets for approved sources, stored in Secret Manager. Follow `docs/release/push-notifications.md` to register Firebase apps, enable Apple Push Notifications, upload the APNs authentication key to Firebase, set GitHub Firebase variables, and grant `cloudmessaging.messages.create` to the API runtime identity. Apply migrations, then verify upload/download, SCIM lifecycle, signed event retries, and push on physical devices in staging. Vendor-specific labor/POS/ticketing adapters remain unimplemented.
7. **Configure and exercise the deployment path.** Establish GitHub-to-GCP Workload Identity Federation, create least-privilege deployer/runtime identities, provision pinned Secret Manager versions, Artifact Registry, Cloud Run and the private bucket, then run the tagged-candidate health gate. Follow `docs/release/cloud-run-api.md`; no GCP resources or API deploy were created in this repository change.
8. **Agree integrations and distribution.** Map the vendor-specific labor/POS/ticketing APIs, field ownership, event mapping, retry behavior, and support contacts. Follow `docs/release/mdm-intune-distribution.md` for managed AppConfig schemas and operator steps for Microsoft Intune / Apple Business Manager; TestFlight alone is not managed-device deployment, and repository templates do not enroll physical devices.
9. **Complete customer security and operations review.** Work through `docs/security/pilot-security-evidence-register.md` and complete `docs/operations/pilot-support-agreement-template.md` with the customer. SOC 2 evidence, independent penetration testing, DPA, insurance, agreed SLA, staffed incident response, monitoring, backups/restore evidence, and event-day support commitments must be supplied and approved; repository templates and gates do not create those attestations or commitments.
