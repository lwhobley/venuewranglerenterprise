# Flutter + Supabase Rebuild — Phase 0 Discovery & Migration Plan

Status: **Phase 0 (Discovery only). No application code has been modified or deleted.**
Scope: Audit of `lwhobley/venuewranglerenterprise` (target repo) and `lwhobley/venuewrangler` (reference repo for mature business logic), and a mapping plan for rebuilding Venue Wrangler Enterprise as a Flutter-first, Supabase-managed application.

---

## 0. How to read this document

- **Reference repo** = `venuewrangler` (Expo Router app + NestJS/Prisma API in `packages/api`, deployed to Cloud Run). This is the source of truth for mature business logic, integrations, and feature breadth.
- **Enterprise repo** = `venuewranglerenterprise` (this repo). It already contains a Flutter prototype (`prototype/venue_wrangler_prototype`) and an *independently evolved* NestJS/Prisma service (`services/api`) — **this is not a copy of the reference repo's API**, it is a narrower, enterprise/pilot-focused backend with its own schema, SSO/SCIM, and a materially different (and more correct) tenant-isolation approach.
- Everything below is organized so Phase 1–4 work can be scoped directly from it. No destructive action has been taken; `services/api` and the reference repo remain untouched.

---

## 1. The single most important Phase 0 finding

**The two existing backends take opposite approaches to tenant isolation, and neither is a drop-in Supabase RLS story:**

| | Reference repo (`venuewrangler/packages/api`) | Enterprise repo (`venuewranglerenterprise/services/api`) |
|---|---|---|
| Isolation mechanism | Application-layer: `AsyncLocalStorage` tenant context (`tenant-context.ts`) + a Prisma Client Extension (`tenant-isolation.extension.ts`) that auto-injects `WHERE venueId = …` into every query when a tenant is bound. Postgres RLS is **enabled but has no per-tenant policies** — documented explicitly in `docs/tenant-isolation.md` as trust-boundary decision "VW-23": the API, not the database, is the real isolation boundary today. | Real Postgres RLS: CI (`ci.yml`) provisions dedicated `venue_migrator` / `venue_app` Postgres roles and runs an actual `test:tenant-isolation` RLS probe against the database. This is architecturally much closer to what Supabase requires. |
| Feature breadth | Very broad: CRM, floor plans/table mgmt, reservations, chat, bar inventory + AI parsing, AI auto-scheduler, "Wrangler" AI operator, Stripe + RevenueCat/Apple IAP billing, Square/QuickBooks/Gusto payroll push, SCIM: **none**. | Narrower, operations/pilot-focused: Issues (report→triage→assign→escalate→resolve, SSE), Staffing (schedule grid, qualifications, vendor staffing), Hospitality (order→fulfill→pickup), Event Closeout, SCIM 2.0, Okta/Entra OIDC SSO with capability-scoped claims, named support-access sessions, MDM/Intune managed config, generic signed/HMAC integration ingestion. No Square/QuickBooks/Gusto/Gemini/Stripe code at all today. |

**Implication for the rebuild:** We should use the reference repo as the source of truth for *business logic and integration behavior* (per the hard requirement), but use the Enterprise repo's **existing RLS/role model as the architectural template** for how Supabase RLS policies should be structured and tested. Neither repo can simply be "ported" — the tenant-isolation code in both is NestJS/Prisma-specific and must be redesigned as native SQL RLS policies, with new tests, per table.

A second notable finding: **no Supabase dependency exists anywhere in the Enterprise repo today** — not in the Flutter prototype's `pubspec.yaml`, not in `services/api`. This is a full backend replacement, not an incremental migration. The Flutter prototype also has no `go_router` and no `supabase_flutter`/`freezed`/`json_serializable` yet — these are new additions required by this plan's Flutter architecture requirements, not already-adopted patterns.

## 2. Current state inventory

### 2.1 Reference repo (`venuewrangler`) — backend (`packages/api`, NestJS 10 + Prisma + Postgres, Cloud Run)

**Prisma schema**: ~90 models / 23 enums. 14 global (non-venue-scoped) models (`User`, `Session`, `AuthAccount`, `PasswordCredential`, `DeviceAttestation`, `AttestationChallenge`, `Venue` itself, `CosmicInsight`, `ObjectDeletionJob`, `RateLimitBucket`, plus 4 pseudonymized retention tables `RetainedTimeEntry`/`RetainedPosCheck`/`RetainedPosLaborPunch`/`RetainedStaffRequest` that intentionally survive venue deletion for wage/compliance retention). ~76 models carry `venueId` and are tenant-scoped, spanning: identity/membership, scheduling/workforce, time & attendance, chat, notifications/push, guests/CRM, reservations/floor plans, POS, billing, payroll, bar inventory, operations (logbook/checklists/event execution), audit, documents, AI usage/budget (`AiUsageEvent`, `AiBudgetReservation`).

**API surface**: ~30 controllers under a global `/api` prefix, each with its own `v1/...` route. Full domain list: auth, billing (Stripe + RevenueCat webhooks), health, support/contact, push tokens, device attestation (iOS App Attest only — no Android/Play Integrity today), app/profile/venue bootstrap, staff + AI-assisted CSV import, bar inventory (+ AI parsing, reports, purchase orders), chat (S3-backed images), CRM (leads/BEOs/contracts/forecast), documents (ClamAV-scanned), floor plans/tables/waitlist, guests (+ public leads webhook), insights ("cosmic insights", global not venue-scoped), reservation integrations, operations (manager dashboard, AI daily brief, command center, checklists), the "Wrangler" AI assistant + AI operator (plan/execute), payroll (Gusto OAuth + generic Square/QuickBooks push), POS (public ingest webhook + reporting), reservations (public ingest webhook + CRUD), scheduling (+ AI auto-scheduler, shift swaps), staff requests, time clock (geofenced + App-Attest-checked), workforce (join requests).

**Integrations** (file-level, with env vars and webhook/OAuth/schedule characteristics) are cataloged in full in §3 below.

**Webhooks** (all with signature/secret verification): Stripe (`verifyStripeSignature`, HMAC-SHA256 of `timestamp.rawBody`, 300s replay tolerance, multi-secret rotation support), RevenueCat (bearer secret, constant-time compare), POS ingest per-venue (`PosConnection.webhookSecret`, hashed at rest), reservation ingest per-venue (`ReservationConnection.webhookSecret`), guest leads webhook (`Venue.leadsWebhookSecret`, rotatable, replay-protected via `x-webhook-id`/`x-webhook-timestamp` + idempotency key). All secrets are stored as `sha256:<hex>`, never in plaintext.

**Scheduled jobs**: in-process `@nestjs/schedule` crons (reservation reminders hourly, chat-image cleanup hourly, general object-deletion drain hourly, long-shift/missed-clockout alerts every 10 min) plus one standalone Cloud Run Job (`src/retention.ts`) that runs audit-log cleanup, retained-time-entry cleanup, and expired-attestation-challenge cleanup, with its own Sentry init and failure reporting.

**Auth/authz**: Custom PBKDF2 (600k iterations) password auth combined sign-in/up endpoint, email verification codes, password reset, session-table-backed JWT (live DB lookup for instant revocation, not purely stateless), a "profile adoption" flow for merging invite-created orphan profiles into real accounts, 4-tier role model (`staff` < `server` < `manager` < `owner`/`admin`, equal rank) plus an `allAccess` support/internal bypass flag.

**Encryption at rest**: `payroll-crypto.ts` — AES-256-GCM with random IV, versioned payload format, key from `SHA-256(PAYROLL_TOKEN_KEY)`, used to encrypt Gusto/Square/QuickBooks OAuth tokens before persisting; a separate HMAC-signed, expiring OAuth `state` parameter binds venueId+expiry+provider for CSRF/replay protection during OAuth callbacks.

**Hard external dependencies flagged for replacement**: AWS S3 (chat images, boot fails without creds), ClamAV daemon (document malware scanning), Resend (transactional email).

**Test coverage** (112 spec files) clusters around: tenant isolation (6 files), idempotency/webhook replay (3), concurrency (3: shared-lease, scheduling, inventory movement), auth/session/roles (6), billing (4), audit redaction (2), attestation/geofencing (2), rate-limit/abuse hardening (6), payroll integrations (3), POS (2), AI scheduling (3), Wrangler AI operator (8), retention/lifecycle (3), DB migration integrity/prod-safety guards (3), plus per-module controller/service specs and one full e2e spec.

**Gaps noted in the reference repo itself** (to resolve, not copy): `.env.example` is missing several vars actually used in code (`SQUARE_APPLICATION_ID/SECRET`, `SQUARE_REDIRECT_URI`, `QUICKBOOKS_CLIENT_ID/SECRET`, `QUICKBOOKS_REDIRECT_URI`, `GUSTO_CLIENT_ID/SECRET`, `GUSTO_REDIRECT_URI`, `PAYROLL_TOKEN_KEY`, `GEMINI_WRANGLER_OPERATOR_MODEL`, `APP_ATTEST_BUNDLE_ID`); no SCIM exists there at all; no Android/Play Integrity attestation exists there at all.

### 2.2 Reference repo (`venuewrangler`) — mobile app (Expo Router, root of repo)

**Screens**: full auth flow (welcome/sign-in/register/verify-email/reset-password/invite-only venue creation/invite-check/invite-accept/team-choice/workplace-search/join-pending), 13 tab screens (home dashboard, schedule, staff, clock, floor, reservations, guests/CRM, sales, reports, bar-stock, documents, chat, integrations, profile), and modal/root screens for checklists, event command center, floor editor, logbook, the "Wrangler" AI assistant, host stand, help, inventory/recipes, join requests, full reservations management, first-run setup, venue settings, and billing (Stripe checkout/portal links + RevenueCat IAP paywall).

**Data layer**: `lib/railway-hooks.ts` is a ~120-entry route table (`"namespace.fnName"` → REST path) wrapped in thin React Query hooks (`useQuery`, `useQueryState` with 402-subscription-required handling, `useMutation`/`useAction` with cache invalidation). `lib/api-client.ts` is the underlying fetch wrapper: bearer token + `X-Venue-Id` header, 401/403("no active membership") forces sign-out, 30s default timeout (120s for uploads), and an "ownership guard" that rejects in-flight requests if the local session identity changed mid-request (race-condition defense after account/venue switch).

**Client-side integration posture (confirmed clean)**: no Stripe SDK in the client (hosted checkout/portal URLs only); Square/QuickBooks/Gusto connect UI is a plain form that POSTs provider+credentials to the API — all OAuth exchange happens server-side; Gemini/AI inference is 100% server-side, the client only renders results and allow-lists which server-suggested "plan" routes it's willing to navigate to; Sentry uses a public DSN with PII scrubbing and dev-mode disabled; RevenueCat uses a public SDK key. **No server-only secret of any kind was found in the mobile client.**

**Device attestation**: iOS-only today, via a custom Expo native module (`modules/app-attest`) wrapping `DCAppAttestService` (generateKey/attestKey/generateAssertion), with a deterministic canonical-JSON payload format that must stay byte-identical between client and server. No Android/Play Integrity client code exists.

**Offline support**: exactly one offline queue exists today (`lib/offline-inventory-queue.ts`, bar-inventory stock movements only) — per-owner scoped, cross-tab-safe on web, retry/backoff on reconnect. No app-wide offline queue exists; this is a gap relative to this plan's requirement to offline-enable tasks/checklists/incidents/media-retry.

**Secure storage**: `expo-secure-store` used for the App Attest key id and for the session token (native); web deliberately uses `sessionStorage`, not `localStorage`, to avoid XSS-persistent tokens.

**Most important doc**: `docs/tenant-isolation.md` — already covered in §1.

### 2.3 Enterprise repo (`venuewranglerenterprise`) — current state

**Flutter prototype** (`prototype/venue_wrangler_prototype`): Flutter ≥3.5, `flutter_riverpod` (state mgmt already matches this plan's requirement), `dio` (REST client, no `supabase_flutter`), plain `Navigator` (no `go_router` yet), `flutter_secure_storage`, `connectivity_plus`, `cryptography`, `flutter_appauth` (OIDC/PKCE), `firebase_core`/`firebase_messaging` (FCM push). Existing feature folders: `auth/` (OIDC/PKCE + support-access), `config/` (API base URL + MDM managed-config reader), `features/hospitality/`, `features/issues/` (offline outbox + encrypted evidence store), `features/notifications/` (push routing), `features/operations/` (the single Dio API client with an offline-cache layer, staffing schedule grid, vendor staffing, venue structure, wall-clock helpers, command palette). 13 existing test files already validate: offline session reads, outbox durability, sync-retry-on-reconnect, MDM config parsing, push→tab routing, responsive nav breakpoints, encrypted evidence lifecycle, staffing quick-view filters, schedule-grid keyboard nav, venue-timezone correctness (incl. DST), and the command palette. This is a real foundation, not a stub — Phase 1/2 should extend it, not discard it.

**`services/api`** (NestJS 11 + Prisma 6 + vitest, OpenTelemetry instrumented): ~50 Prisma models covering Organization/Venue/Event, Issues (+domain events, idempotency `CommandReceipt`), Operational Tasks, Hospitality orders/fulfillment/evidence, Staffing (shifts/demand/breaks/attendance/unavailability/qualifications/vendor requests), Event Closeout (+followups/audits/corrections), generic Integration ingestion (events, identifiers, transforms, checkpoints, dead-letter), Support Access sessions, Push Devices, Tenant Setup audit. As noted in §1, this backend already enforces real Postgres RLS and has a CI-verified tenant-isolation test harness — use this as the design reference for the new Supabase RLS policies, not as code to port (it's still NestJS/Prisma, which must go per the hard constraint).

**Existing planning docs** (must not be contradicted or silently duplicated):

Additional present-but-unaudited workflows to review before Phase 1: `api-deploy-drift.yml`, `branch-api-parity.yml`, `site-branch-parity.yml`, `retention-cleanup.yml`, `prowler-compliance.yml` (GCP-specific SOC2 scanning — needs a Supabase-era equivalent), `database-backup.yml`, `codeql.yml`, `dependency-audit.yml`.

## 5. Functionality that cannot be exactly replicated in Supabase Edge Functions (and why)

1. **ClamAV malware scanning for documents.** Edge Functions are short-lived, stateless Deno invocations with no support for running a persistent scanning daemon or large signature database. A functionally equivalent design needs either (a) an external managed anti-malware API called from an Edge Function, or (b) a small always-on scanning service running outside Supabase that the Edge Function hands a signed, short-lived download URL to, writing a `scan_status` back via a service-role call when done. This must be decided and documented before documents/evidence upload RLS policies are finalized, since "upload complete" cannot be marked true until scan status is known.

2. **Device attestation verification (Apple App Attest / Google Play Integrity).** Both require parsing vendor-specific binary formats (CBOR/COSE for App Attest, signed JWT with Google's rotating public keys for Play Integrity) and validating against Apple/Google's own trust roots. This is possible in Deno (Edge Functions can `fetch` and have WebCrypto), but no first-party Supabase helper exists for either, and reference-repo code for this (`common/app-attest.ts`) is Node-specific, not directly portable. Android/Play Integrity has **no prior implementation in either repo** — it is net-new work, not a port.

3. **In-process `@nestjs/schedule` cron jobs with long-running batch work** (the standalone `retention.ts` job touches multiple large tables sequentially; the reference repo already runs it as a separate Cloud Run Job rather than in-process for this reason). Supabase Edge Functions have a maximum execution duration; a job that currently runs unbounded on Cloud Run may need to be redesigned as a `pg_cron`-scheduled SQL function that processes in batches, or an Edge Function that processes one page per invocation and re-triggers itself, to stay within the duration limit. This must be load-tested against real data volumes before cutover, not assumed to "just work."

4. **The `AsyncLocalStorage` + Prisma-extension automatic tenant-scoping used in both existing backends.** This is a request-scoped, imperative mechanism tied to a long-lived Node process; Supabase RLS is a declarative, per-row, per-statement mechanism evaluated inside Postgres itself. There is no way to "port" the extension — every tenant-scoped table needs its own hand-written, hand-tested RLS policy. This is the single largest and riskiest piece of net-new work in the whole migration (see §1), and it is why Phase 1 explicitly requires RLS + authorization tests to exist **before** feature screens are built on top of them.

5. **Live DB-backed session revocation ("logout-all", instant revoke) exactly as implemented today.** Supabase Auth has its own session/refresh-token model; reference-repo semantics (an app-level `Session` row checked on every request) are not identical to Supabase's JWT+refresh-token lifecycle. Equivalent behavior (admin-forced sign-out of all sessions) is achievable via Supabase Auth's admin API from an Edge Function, but needs explicit design and testing rather than assuming parity.

6. **SSE (Server-Sent Events) for live Issue updates** (Enterprise `phase-6-architecture.md`). Supabase Realtime (Postgres logical replication over WebSockets) is the natural replacement, but it is a different protocol and reconnection/backoff model than SSE — client code and tests built around SSE semantics (if any exist beyond the architecture doc) will need to be rewritten against Realtime's actual behavior, not simply re-pointed.

## 6. Open questions / blockers requiring a decision before Phase 1 code begins

- **OQ-1 (product scope reconciliation):** The Enterprise repo's own IA docs (phase-2 through phase-6) define a narrower, ops-focused product (Today/Issues/Staffing/Hospitality/Event Closeout) than the reference repo's full feature set (CRM, floor plans, bar inventory AI parsing, chat, AI auto-scheduler). This plan's "operational features to preserve" list spans both. **Needs an explicit decision**: fold all reference-repo features into the existing Enterprise IA (as new top-level areas or sub-areas of the existing ones), or treat some reference-repo features as deferred/out-of-scope for the Enterprise product. Recommend resolving this at the start of Phase 2, per-module, rather than blocking Phase 1 foundation work.
- **OQ-2 (RevenueCat/Apple IAP billing):** present in the reference repo, not mentioned in this rebuild's integration list (which names Stripe only). Decide whether to carry it forward as a second billing path or consolidate on Stripe + hosted checkout only.
- **OQ-3 (malware scanning provider):** needs a named external service or self-hosted scanner before Storage upload-completion policies can be finalized (see §5.1).
- **OQ-4 (Android attestation vendor details):** Play Integrity API project/credentials are not yet established anywhere in either repo; this is genuinely new infrastructure, not a migration of existing config.
- **OQ-5 (SCIM + SSO identity provider specifics):** `enterprise-sso-setup.md` documents the *shape* of `SSO_PROVIDERS_JSON`/capability claims but real customer IdP registration is listed in `pilot-readiness.md` as an external gate still pending — Supabase Auth OIDC provider setup is blocked on the same external dependency, not on this migration's code.
- **OQ-6 (secrets not yet documented anywhere):** `PAYROLL_TOKEN_KEY` and all three payroll providers' OAuth client secrets exist only in the live Cloud Run deployment's Secret Manager, not in any `.env.example` in either repo. These must be sourced from whoever holds deployment access before Edge Function secrets can be configured — this plan does not fabricate or guess at their values.

## 7. Recommended next milestone

Phase 0 is complete: both repositories have been audited, the mapping table above covers every major entity/endpoint/integration/webhook/scheduled job, and the five items in §5 identify what cannot be directly ported. No destructive or irreversible action has been taken.

**Recommended Phase 1 entry point**, in order:
1. Resolve OQ-1 enough to name the initial Postgres schema's table list (organizations, venues, memberships, roles, audit_log — the foundation row in §4's mapping table).
2. Stand up Supabase local dev + initial migration framework, with RLS enabled and **default-deny** on every table from the first migration, per the hard constraint in the top-level instructions.
3. Write the authorization test suite for that foundation schema (role × table × tenant, positive and negative) **before** any Flutter screens are built against it — this directly addresses the highest-risk item identified in §1 and §4.
4. Add `go_router`, `supabase_flutter`, `freezed`/`json_serializable` to the existing Flutter prototype (not a rewrite — extend `prototype/venue_wrangler_prototype`, which already has Riverpod, secure storage, and a tested offline-outbox pattern worth keeping) and wire up Supabase Auth alongside the existing OIDC/PKCE flow.
5. Do not begin Square/QuickBooks/Gusto/Gemini/Stripe/attestation Edge Function work until the foundation schema's RLS tests are green — those integrations all depend on `organization_id`/`venue_id`/role checks that must already be correct.

`services/api` and the reference repo remain the comparison/reference implementations and must not be deleted until parity, testing, and explicit approval per the top-level execution rules.
